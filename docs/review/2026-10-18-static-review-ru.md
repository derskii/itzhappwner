# Статический аудит Happwner API 102

Дата: 18 октября 2026 года. Проверены исходники форка, затронутые прежним аудитом 1.3.2, и новые участки профилей, IPC, сетевого моста и конвертации. Это проверка текста исходников и ресурсов: компиляцию, unit/instrumentation-тесты, установку и запросы подписки не запускал.

## Исправлено

- Экспортированный `SettingsProvider` больше не доверяет любому установленному приложению. В настройках добавлен явный список разрешённых приложений; доступ сверяется с фактическим UID вызывающего процесса и SHA-256 текущего сертификата подписи. Пакет не может добавить себя через `MODULE_LOADED`.
- Захват Android ID переведён с доверенного broadcast на проверяемый вызов `ContentProvider`. ID и URL проходят проверки формата/размера; URL-история ограничена 100 записями. Данные профиля в broadcast не передаются; сообщения обновления адресуются только выбранным пакетам.
- Сервис моста слушает только `127.0.0.1`, требует случайный локальный bearer-ключ и ограничивает число клиентов, строку запроса, URL и тело ответа. Для строки запроса задан общий дедлайн 30 секунд, для сетевого запроса — 60 секунд; запросы закрываются при остановке сервиса. При переходе на другой origin заголовки профиля удаляются, ошибки upstream возвращаются с HTTP-ошибкой.
- Общий HTTP-клиент проверяет URL и заголовки, ограничивает тело 32 MiB, redirects — пятью переходами, устанавливает per-I/O таймауты и общий дедлайн. Секретная query-строка моста не записывается в лог.
- Старые ошибки конвертера, которые могли ослабить Xray-условие до безусловного правила, исправлены: неподдерживаемые отрицания, `ext:`-фильтры, неверные порты и неизвестные значения приводят к пропуску целого правила. Объединение конфигураций переносит inbound и переименовывает ссылки. Исправлены специальные символы в URI-креденшалах, исходные VMess security/alterId и обработка нескольких outbound.
- Результаты сетевых запросов не смешиваются между быстрыми последовательными URL; очистка результата отменяет активную загрузку. Расшифровка/конвертация выполняется вне главного потока, устаревшая расшифровка не меняет новый URL, входящая ссылка сохраняется при пересоздании Activity.
- Повреждённые сохранённые профили архивируются и не должны аварийно останавливать загрузку профиля. Добавлены недостающие accessibility-описания, контраст текста, моноширинный вывод и ограничение высоты поля URL.
- Вход API 102 описан через `XposedModule`, `META-INF/xposed/java_init.list` и `module.prop`; сохранён отдельный legacy API 82 вход. В манифест добавлено описание модуля для современного менеджера.

## Статические проверки

- `git diff --check` завершился без ошибок.
- XML-парсер Python прочитал все 81 XML-файл в `app/src/main`.
- Повторяющихся имён строк в базовом и русском `strings.xml` не найдено; новые строки выбора приложений есть в обоих языках.
- Ссылки на старый неподписанный `ID_CAPTURED`-receiver и доверие к любому вызову provider удалены. Поиск оставшихся вызовов `IdentityCodec.bridgeUrl` показал передачу токена во всех местах.

## Повторная проверка

- Закрыт ещё один IPC-дефект: удалён экспортированный `SETTINGS_REQUEST`, который любой процесс мог использовать для массового пробуждения разрешённых приложений. Запрашивающий модуль уже получает первичные настройки напрямую через caller-проверяемый provider.
- На `BootReceiver` добавлено требование системного разрешения `RECEIVE_BOOT_COMPLETED`, чтобы стороннее приложение не могло разбудить мост поддельным boot-broadcast.
- Исправлен тестовый fixture: некорректный заголовок теперь помещается прямо в JSON, чтобы тест проверял отказ декодера, а не падал раньше при вызове encoder.
- После этих правок повторены `git diff --check`, разбор XML и проверки строковых ресурсов; компиляция, тесты и runtime-проверки не запускались.

- `bash gradlew :app:assembleDebug` остановился до запуска Gradle: wrapper не смог скачать Gradle 9.3.1 из-за недоступной сети (`Network is unreachable`). Локального Gradle-дистрибутива нет.
- Найденный в `app/build/outputs` APK датирован раньше последних исходников, поэтому он не выдаётся за свежую сборку.

- Компиляция проекта и тесты фактически не стартовали.

## Что осталось проверить на устройстве

- Результат не подтверждён компиляцией, тестами, R8/minify или реальным устройством; такой проверки в этой версии аудита нет.
- `minSdk 26` гарантирует запуск самого приложения, но не каждый современный API 102 framework callback на Android 8–8.1. В известной реализации Vector `onPackageReady` вызывается начиная с API 28; legacy-вход сохранён, обе ветки требуют проверки на целевых менеджерах.
- Хуки меняют Java `URLConnection` и доступный приложению OkHttp. Нативные стеки, Cronet и обфусцированные копии OkHttp могут обходить их; перенаправления в стороннем клиенте контролируются самим клиентом.
- Фактический Happ User-Agent и заголовки ОС/модели публично не установлены. Предустановки с такими полями — редактируемые шаблоны совместимости; сервер может их игнорировать. Сетевые запросы для проверки не выполнялись.
- До Android 14 broadcast `MODULE_LOADED` нельзя надёжно связать с UID отправителя. Подделка для уже разрешённого пакета может дать ложный статус LSPatch; выдача профиля остаётся закрыта проверкой UID и сертификата в provider.
- Несохранённый черновик редактора устройства может пропасть при полном пересоздании Activity. Встроенный быстрый scroll и поведение темы/доступности требуют runtime-проверки.

Современный API 102 документирует Java entry через `XposedModule`, файл `java_init.list` и настройки `module.prop`: [руководство LSPosed](https://github.com/LSPosed/LSPosed/wiki/Develop-Xposed-Modules-Using-Modern-Xposed-API). Статическое совпадение структуры с руководством не доказывает успешную загрузку модуля в конкретной версии framework.
